# Netmera REST API — OpenAPI specification

`netmera-rest-api.yaml` is the single source of the REST API reference in the Netmera
Developer Guide. Every OpenAPI block on a guide page reads this one file, from this one URL:

```
https://raw.githubusercontent.com/ecemnaz1/netmera-rest-api/main/netmera-rest-api.yaml
```

GitBook holds it as the spec `netmerarestapiyaml`. No other file, branch or repository feeds
the guide. Do not register another spec for the guide, and do not upload the file to GitBook
by hand: a manual upload is overwritten by the next push.

## How an update reaches the docs

1. Edit `netmera-rest-api.yaml` on a branch and open a pull request.
2. CI parses the file, lints it with Redocly, runs the security guard (see Security rules)
   and checks that no verified response was dropped.
3. Merge to `main`. GitBook reads the raw URL on its own schedule. To publish immediately,
   open the spec in GitBook (Settings > OpenAPI) and click **Check for updates**.

The URL must contain `main`, not a commit SHA or another branch: a pinned URL never
refreshes, and a branch URL stops working when the branch is deleted. The repository must
stay public, because GitBook cannot read a source behind a login.

## Security rules

`main` is read directly by GitBook (checked every six hours), by the **Download OpenAPI spec**
link and by the Scalar API client, so a change on `main` reaches readers without another
review. `scripts/guard_spec.py` runs in CI on every pull request and push and fails when:

- `servers` is anything other than `https://restapi.netmera.com`, or a path or operation
  overrides it. A changed server would send the API key readers type into Test it elsewhere.
- authentication is not the `X-netmera-api-key` header applied globally, or an operation
  overrides or removes it.
- an endpoint that deletes in bulk shows the Test it panel. Delete Users, Delete Users
  Permanently, Delete Profile Attribute from All Users and Change Segment Status carry
  `x-hideTryItPanel: true` (`MUST_HIDE_TRY_IT` in the script).
- an endpoint that can send to many users shows Test it without the warning. Send Bulk
  Notification, Send Transactional Notification, Start, Update or End Live Activity, Send
  Email or SMS and Send Bulk Email (`BULK_SEND`) keep Test it open, so each one opens its
  description, right after the first paragraph, with a `{% hint style="danger" %}` block that
  starts "**Requests sent from Test it are real.**", and its first example must not set
  `sendToAll: true`; the bulk examples target the `test-users` tag, which fails with code
  `2009` when the tag does not exist. Any new endpoint whose body has `sendToAll` is held to
  the same rule automatically.
- the spec contains active HTML (`<script>`, `<iframe>`, event handlers, `javascript:` links),
  plain-http links or the GitBook request proxy extension.
- any tracked file contains something that looks like a credential (API key, token, private
  key, JWT, FCM token), an email address outside `example.com`/`.org`/`.net` and the
  `example`, `example1`–`3` and `info` addresses at `netmera.com`, a Turkish mobile number other
  than `905000000000`, or a link to a host that is not on the allowlist in the script. Add a
  host to the allowlist only for a public site the docs really link to.

See `SECURITY.md` for how to report a problem and what to do if a credential was committed.

Never put a real API key, token, customer identifier, email address or phone number in the
spec, the README or a commit, including in an example or a captured response.

## What the spec describes

The spec describes the behaviour of the Netmera REST API in production. Request and response
examples were checked against the API.

**The live API is the authority.** Where the earlier Developer Guide text disagrees with the
API, the spec follows the API.

**What lives where.** This file carries every endpoint: parameters, examples, responses and
error codes. GitBook generates one page per endpoint from it, ordered and grouped as the
`paths` and `tags` here are ordered. Concepts that apply to every endpoint (authentication,
external IDs, limits, pagination, retries, the error code table), guides and recipes are
written as pages in the GitBook space and link to the endpoint pages.

## Conventions

- **`summary` is the page title in the reference:** an action in Headline Case ("Send Bulk
  Notification", "List Segment Users"). The method and path are shown on every page and in the
  sidebar badge, so the title says what the endpoint does.
- **Group pages list their endpoints as cards.** Each tag description is a one-paragraph intro
  followed by a card per endpoint (or per sub-group), so clicking a group never lands on an
  empty page. The cards are generated by `scripts/tag_cards.py` from the operation titles and
  the first sentence of each description; re-run it after adding, renaming or moving an
  operation. Card links must be absolute URLs: relative links do not resolve in GitBook tag
  descriptions.
- **Notes are collapsible.** Each operation description ends with its Notes wrapped in
  `<details><summary>Notes</summary> … </details>`, so the page opens with the summary,
  Capabilities and How it works, then the request and responses. GitBook always renders the
  description above the request block; there is no way to place text after it.
- **Order matters.** Tags are listed in the order readers need them, and `paths` are ordered
  within each tag by the typical flow (register before delete, list before get). Each tag has
  `x-page-title`, `x-page-icon` and a user-focused `description`; channel permission tags are
  grouped under `x-parent: Channel Permissions`.
- **Page IDs follow the page's place in the tree.** Moving an operation to another tag, or
  changing a tag's title or parent, changes its generated page ID. Links from guides and
  recipes to that page must then be re-pointed.
- **`x-netmera-verified: <date>`** marks a response confirmed against the API. It is
  invisible to readers. `scripts/check_verified.py` fails the build if a marker disappears.
  No other `x-netmera-*` extension is used.
- **Error responses are listed per operation only where they were observed** for that
  operation. The full error code table lives in the Errors page of the GitBook space. Redocly's
  `operation-4xx-response` warning on the few operations without errors is expected.
- **Parameters the API accepts but ignores are left out.** Documenting them would suggest
  they do something.
- **Examples use fictional values only**: `example@netmera.com`, `+90xxxxxxxx`,
  `your_rest_api_key`, small round numbers. Names of button sets, categories, sounds and
  attributes in examples are placeholders; each application uses its own.
- `info-license` is reported by Redocly because no license is stated. It is expected.

## API behaviour that differs from the earlier guide text

Keep these as they are; they were verified against the API.

- A missing or invalid API key returns **401** with code `2010`. **403** with code `2021`
  means the caller's IP address is not on the allowlist.
- Error bodies are `{"code": N, "error": "..."}`. Some failures return an RFC 9457 problem
  detail or plain text instead; see the Errors page of the GitBook space.
- `sendNotification` returns `{}`; `sendBulkNotification` and `sendEmailAndSms` return the
  notification key. `notificationKey` must be sent to `sendNotification` as a string.
- `deleteUsers` does not delete a user; it marks the user as untracked. `deleteUsersPermanently`
  deletes in the background, and only when permanent deletion is enabled for the application.
- `sendEmailWithAttachment` is served on `https://restapi.netmera.com` and accepts at most
  1 MB per attachment.
- A segment target written as `{"$or": [...]}` is rejected; use an array of segment names.
